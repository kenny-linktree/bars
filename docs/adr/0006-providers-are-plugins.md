# Providers are plugins, run out of process, with presentation in the snapshot

Bars needed a way for anyone to add a provider without changing Bars or sending a pull request. Each provider is now a plugin directory (`plugin.json` plus one `plugin.py`) under `~/Library/Application Support/Bars/plugins`; Claude, Codex, Cursor and Devin are standard plugins installed the same way. The collector reads only the manifest and runs `plugin.py` inside the per-provider worker process it already had, so a faulty plugin can hang, crash, print or return nonsense and cost only its own row one attempt. Everything the native readers used to know about a particular provider (setup steps, usage link, mini-bar selection, estimated resets, balance notes) moved into the plugin manifest and result and travels in snapshot version 2, so a custom provider looks exactly like a standard one and no Swift code names a provider.

Considered: loading plugins into the coordinator process (rejected: one bad import or a pickled result would take every provider down, and Swift presentation would still be hardcoded); keeping Swift's per-provider switch statements and rendering unknown providers generically (rejected: two code paths and second-class custom providers); wrapping workers in `sandbox-exec` (rejected for now: deprecated, interferes with Keychain lookups, hard to test; plugins run as the user, like any script, and the trust statement says so).

Consequences: updates refresh standard plugin files only when they are unchanged since the installer wrote them, recorded by digest in `plugins/.installed.json`; an edited file is kept with a warning, which is the agreed behavior for people who tweak a standard plugin. Providers are ordered by id, the set can be empty, and the readers must cope with both. The public plugin interface is the `bars_plugin` package and the manifest; the rest of the collector is private. Changing a snapshot field now means changing the contract, the SDK and the readers together.
